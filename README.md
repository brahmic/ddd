# Руководство по применению DDD

Две связанные части для проектирования и реализации предметной модели:

- [Ядро](core/principles.md) — понятия DDD и технологически независимые рекомендации.
- [Профиль Laravel](laravel/README.md) — конкретные решения на PHP и Laravel со ссылками на ядро.

Обоснование общего правила хранится в ядре. Профиль ссылается на него и описывает механизм, ограничения и проверку реализации. Ядро не зависит от профиля.

Основная точка входа для проекта на Laravel — [README профиля](laravel/README.md). Для изучения методологии начните с принципов и стратегического проектирования.

## Как применять в проекте

1. Согласуйте с носителем бизнес-знаний термины, сценарии, ограничения и спорные случаи.
2. Пройдите [порядок разработки](core/workflow.md).
3. Выберите профиль реализации. Укажите его в документации проекта.
4. Зафиксируйте отличающиеся решения с помощью [шаблона ADR](templates/architecture-decision.md).
5. Оценивайте архитектуру по [критериям ядра](core/review-criteria.md) и, при использовании Laravel, [критериям профиля](laravel/review-criteria.md).

Копируйте папку целиком: внутренние ссылки относительные. Имена бизнес-объектов в примерах иллюстративны; правила предметной области каждого проекта нужно установить заново.

## Как читать правила

Идентификаторы принадлежат этому руководству, а не внешнему стандарту DDD.

| Префикс | Значение | Как применять |
| --- | --- | --- |
| `DDD-` | Понятия и принципы предметного моделирования | Применять к соответствующей модели и её контексту |
| `ARCH-` | Архитектурные рекомендации, поддерживающие модель | Выбирать по условиям задачи; фиксировать варианты |
| `TEST-` | Рекомендации по проверке поведения и границ | Подбирать проверки под риск и контракт |
| `LAR-` | Решения профиля Laravel | Действуют после принятия профиля проектом |

Применимость описана рядом с правилом. Наличие раздела о событиях или репозиториях не требует создавать соответствующие классы для каждого сценария. Каталог из четырёх слоёв также не является доказательством применения DDD.

Заголовок с идентификатором служит устойчивым якорем. Ссылайтесь, например, на [DDD-INV-01](core/domain-model.md#ddd-inv-01). При изменении смысла правила обновляйте связанные документы; при замене идентификатора оставляйте перенаправляющий раздел с объяснением.

## Для разработчика и ИИ-агента

До изменения кода изучите соглашения целевого проекта, выбранный профиль и затрагиваемые правила ядра. Различайте подтверждённое бизнес-правило и предположение. При неизвестном правиле зафиксируйте вопрос и продолжайте работу, которая от ответа не зависит.

Предлагайте минимальное изменение, сохраняющее инварианты и границы. Не расширяйте задачу созданием всех перечисленных паттернов. В описании результата укажите реализованный сценарий, принятые решения и выполненные проверки.
