# Методические материалы по DDD

> **Важно: назначение документации**
>
> Вся документация этого репозитория — методический материал для изучения DDD и осмысленного проектирования. Она не является прямой инструкцией к реализации, scaffold или шаблоном проекта. Это относится к ядру, профилю Laravel, примерам кода и деревьям каталогов.
>
> Разработчик должен вдумчиво соотносить рекомендации с предметной областью, бизнес-правилами, ограничениями и существующей архитектурой своего проекта. Применение требует понимания причин и последствий каждого решения, выбора подходящих приёмов и их адаптации. Механическое копирование структуры или создание всех показанных классов не заменяет эту работу.
>
> В зависимости от ситуации, задачи и обстоятельств применимым может оказаться весь описанный подход или отдельные его части. Разработчик самостоятельно определяет уместный объём применения по фактическим условиям на момент принятия решения, учитывая связи между выбранными частями. При изменении условий этот выбор следует пересматривать.
>
> **Избегайте оверхеда, сохраняя приоритет чистой архитектуры.** По умолчанию отдавайте предпочтение понятным обязанностям, явным границам и отделению бизнес-правил от технических механизмов. Дополнительный класс или интерфейс может быть оправдан именно защитой такой границы. Упрощение полезно, когда убирает лишнюю сложность и сохраняет эти свойства; сокращение числа файлов само по себе не является улучшением. Если польза упрощения сомнительна, предпочтение следует отдать сохранению архитектурных границ. Критерий выбора раскрыт в [ARCH-FIT-01](core/principles.md#arch-fit-01).
>
> Чем масштабнее и сложнее проект, чем выше цена ошибки, больше участников и дольше предполагаемый срок сопровождения, тем больший вес следует отдавать чистым архитектурным подходам. В таких условиях явные границы и управляемые зависимости особенно важны: последствия их нарушения затрагивают больше частей системы и дороже обходятся при изменениях.
>
> Описанные соглашения становятся требованиями конкретного проекта только после их осознанного принятия командой с определённой областью действия. Примеры иллюстрируют ход мысли и возможные решения; их состав не является обязательным набором компонентов.

Две связанные части для проектирования и реализации предметной модели:

- [Ядро](core/principles.md) — понятия DDD и технологически независимые рекомендации.
- [Профиль Laravel](laravel/README.md) — конкретные решения на PHP и Laravel со ссылками на ядро.

Обоснование общего правила хранится в ядре. Профиль ссылается на него и описывает механизм, ограничения и проверку реализации. Ядро не зависит от профиля.

Основная точка входа для проекта на Laravel — [README профиля](laravel/README.md). Для изучения методологии начните с принципов и стратегического проектирования.

## Как применять в проекте

1. Согласуйте с носителем бизнес-знаний термины, сценарии, ограничения и спорные случаи.
2. Используйте [порядок разработки](core/workflow.md) как опору для разбора задачи, выбирая относящиеся к ней шаги.
3. Определите, какие рекомендации и решения профиля подходят проекту. Зафиксируйте принятые соглашения и их область действия.
4. Фиксируйте значимые архитектурные решения и их основания; для этого можно использовать [шаблон ADR](templates/architecture-decision.md).
5. Используйте применимые [критерии ядра](core/review-criteria.md) и, при использовании Laravel, [критерии профиля](laravel/review-criteria.md) для обсуждения и проверки выбранных решений.

Если переносите эти материалы в документацию проекта, сохраняйте папку целиком: внутренние ссылки относительные. Имена бизнес-объектов в примерах иллюстративны; правила предметной области каждого проекта нужно установить заново.

## Как читать правила

Идентификаторы принадлежат этому руководству, а не внешнему стандарту DDD.

| Префикс | Значение | Как применять |
| --- | --- | --- |
| `DDD-` | Понятия и принципы предметного моделирования | Применять к соответствующей модели и её контексту |
| `ARCH-` | Архитектурные рекомендации, поддерживающие модель | Выбирать по условиям задачи; фиксировать варианты |
| `TEST-` | Рекомендации по проверке поведения и границ | Подбирать проверки под риск и контракт |
| `LAR-` | Решения профиля Laravel | Действуют после принятия профиля проектом |

Применимость описана рядом с правилом. Наличие раздела о событиях или репозиториях не требует создавать соответствующие классы для каждого сценария. Каталог из четырёх слоёв также не является доказательством применения DDD.

Заголовок с идентификатором служит устойчивым якорем. Ссылайтесь, например, на [DDD-INV-01](core/domain-model.md#ddd-inv-01). При изменении смысла правила обновляйте связанные документы; при замене идентификатора оставляйте перенаправляющий раздел с объяснением.

## Для разработчика и ИИ-агента

До изменения кода изучите соглашения целевого проекта, выбранный профиль и затрагиваемые правила ядра. Различайте подтверждённое бизнес-правило и предположение. При неизвестном правиле зафиксируйте вопрос и продолжайте работу, которая от ответа не зависит.

Предлагайте минимальное изменение, сохраняющее инварианты и границы. Не расширяйте задачу созданием всех перечисленных паттернов. В описании результата укажите реализованный сценарий, принятые решения и выполненные проверки.

## Проверка самого руководства

Из корня репозитория выполните:

```sh
python3 scripts/check-docs.py
```

Нужны Python 3 и PHP CLI 8.3+; дополнительные пакеты не требуются. [Скрипт](scripts/check-docs.py) проверяет внутренние ссылки на файлы и заголовки, уникальность идентификаторов правил и синтаксис PHP-блоков. Та же команда настроена в [GitHub Actions](.github/workflows/docs.yml) для push и pull request, включая изменения самой проверки.

Это проверка документации. Поведение примера, интеграцию с Laravel и гарантии хранения проверяйте в целевом приложении по [сценариям переноса](laravel/example.md#проверки-при-переносе). Внешние ссылки скрипт не запрашивает.
