# Доменная модель

[Навигация](../README.md). Сначала определите [контекст](strategic-design.md#ddd-ctx-01) и [язык](strategic-design.md#ddd-lang-01).

## DDD-ENTITY-01

**Выделяйте сущность, когда важна непрерывная идентичность.**

Изменение имени или состояния не делает объект новой сущностью. Определите, что обозначает идентификатор и в какой области он уникален. Основание: [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), Entities.

**Пример:** отменённая бронь остаётся той же бронью. Идентичность не выводится из равенства всех её полей.

**Варианты:** состояние можно изменять через методы или создавать новое представление той же сущности. Изменяемость сама по себе не превращает сущность в агрегат.

**Проверка:** предметные действия названы явно; общедоступная запись полей не позволяет обойти правила.

## DDD-VO-01

**Объект-значение выражает смысл и сравнивается по значению.**

Используйте его для понятия с собственными правилами, равенством или поведением. Например, интервал бронирования требует начала раньше окончания. Предпочитайте неизменяемые значения; составные части тоже не должны допускать скрытого изменения. См. [Martin Fowler, Value Object](https://martinfowler.com/bliki/ValueObject.html).

**Применение:** повторяющиеся ограничения, единицы измерения, нормализация или неоднозначные примитивы.

**Варианты:** примитив допустим, когда отдельный тип не добавляет полезного смысла. Объект-значение может быть самостоятельным понятием, а не только полем сущности.

**Проверка:** равные значения ведут себя одинаково. Невалидное значение нельзя выдать за валидное через альтернативный конструктор или преобразование.

## DDD-INV-01

**Агрегат сохраняет свои инварианты при завершении операции.**

Агрегат задаёт границу согласованности. Его корень контролирует изменения объектов внутри этой границы. Состав выводится из правил, требующих совместной согласованности. См. [Martin Fowler, DDD Aggregate](https://martinfowler.com/bliki/DDD_Aggregate.html).

**Пример:** бронь содержит интервал и состояние. Операция отмены проверяет состояние и время перед изменением. Внешний код не меняет состояние внутреннего объекта в обход корня.

**Варианты:** агрегат может состоять из одной сущности. Связанные по смыслу объекты не обязательно принадлежат одному агрегату. Предпочитайте небольшую границу, достаточную для инвариантов.

**Проверка:** допустимые и запрещённые переходы описаны примерами. После неуспешной операции объект остаётся в согласованном состоянии. Защита при одновременном сохранении рассматривается отдельно в [ARCH-CONS-01](application.md#arch-cons-01).

Валидность каждого поля отдельно не гарантирует согласованность всего объекта. Если два поля выражают один идентификатор, исключите независимое присвоение либо проверьте их равенство. Аналогично проверяются связанные даты, суммы и единицы; набор корректных VO не заменяет межполевой инвариант.

## DDD-SVC-01

**Доменный сервис выражает предметную операцию, которой нет естественного места в сущности или значении.**

Его контракт использует язык контекста. Выделение сервиса оправдывается распределением ответственности, а не длиной метода. Основание: [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), Services.

**Пример:** политика рассчитывает допустимую компенсацию по нескольким предметным значениям. Последовательность «получить — рассчитать — сохранить» принадлежит [сценарию](application.md#arch-use-01).

**Варианты:** сначала рассмотрите поведение сущности или значения. Если нужны внешние сведения, передайте их или явно выразите потребность контрактом.

**Проверка:** сервис содержит бизнес-решение; техническая координация не скрывается под доменным названием.

## DDD-FACT-01

**Создание и восстановление должны сохранять смысл модели.**

Фабрика полезна, когда сборка объекта сложна. Простой конструктор или именованная операция создания достаточны для простого случая. Восстановление существующего объекта сохраняет его идентичность и не повторяет эффекты первоначального создания.

Это практическая рекомендация на основе роли Factories в [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf).

**Пример:** новая бронь создаётся подтверждённой. Восстановление отменённой брони не создаёт новое событие отмены. Проверка структурной целостности сохранённых данных отличается от запрета создавать новую бронь с началом в прошлом.

**Варианты:** создание через конструктор, фабричный метод или отдельную фабрику. Повреждённые данные требуют явного решения: отказ загрузки, миграция или отдельная диагностическая модель. Нельзя без договорённости объявлять их валидными.

**Проверка:** восстановление исторических данных не применяет новые правила создания задним числом и не обходит действующие инварианты произвольно.

## DDD-REPO-01

**Репозиторий предоставляет доступ к модели в терминах её объектов.**

Контракт выражает потребность получить и сохранить агрегат, скрывая организацию хранения. См. [Edward Hieatt и Rob Mee, Repository](https://martinfowler.com/eaaCatalog/repository.html).

**Применение:** когда сценарию нужна работа с доменной моделью и её жизненным циклом.

**Пример:** загрузить бронь по идентификатору и сохранить результат отмены. Отдельный репозиторий для каждой таблицы или вложенной сущности обычно обходил бы границу агрегата.

**Варианты:** запрос списка может возвращать проекцию через [контракт чтения](application.md#arch-read-01). Для внешнего поиска уместен gateway; название Repository стоит использовать, если семантика действительно похожа на доступ к коллекции доменных объектов.

**Проверка:** контракт не выдаёт наружу средство построения запросов или внутренний формат поставщика. Отсутствие объекта и конфликт сохранения описаны явно.

## DDD-EVENT-01

**Доменное событие обозначает значимый для модели свершившийся факт.**

Имя описывает произошедшее: «бронь отменена». Событие содержит необходимые для понимания факта данные. Механизм доставки выбирается отдельно. Основание: [DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), Domain Events.

**Применение:** другие действия действительно зависят от факта, либо история фактов имеет предметную ценность.

**Варианты:** локальная обработка, последующая публикация внешнего события или отсутствие событий в простом сценарии. Внешний контракт может иметь собственную форму и версию.

**Проверка:** неудачная операция не публикует факт как состоявшийся. Повторная обработка учитывается по [ARCH-EFFECT-01](application.md#arch-effect-01).
