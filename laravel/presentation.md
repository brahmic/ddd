# HTTP, CLI и задания

[Профиль](README.md).

## LAR-ENTRY-01

Основания: [ARCH-USE-01](../core/application.md#arch-use-01), [ARCH-CONTRACT-01](../core/boundaries.md#arch-contract-01).

**Решение профиля:** точка входа преобразует внешние данные в вызов сценария и формирует ответ своего протокола.

| Точка входа | Подготовка | Вызов и ответ |
| --- | --- | --- |
| HTTP | Аутентификация, проверка формы, доверенный идентификатор пользователя | Прикладной сценарий → JSON, страница или иной HTTP-ответ |
| CLI | Аргументы, опции, полномочия оператора | Тот же сценарий → вывод и код завершения |
| Job | Данные задания, проверка применимости и полномочий | Тот же сценарий → подтверждение обработки или согласованный повтор |

Для HTTP профиль рекомендует FormRequest при нетривиальной проверке входа. Используйте `validated()`, `safe()` или типизированные геттеры. Это варианты доступа к проверенным данным. Механизм описан в [Validation](https://laravel.com/docs/13.x/validation#form-request-validation).

Валидация формы не заменяет защиту инвариантов: объект может измениться после проверки, а сценарий может прийти из другой точки входа. Проверку доступа из FormRequest или middleware согласуйте с доступом в сценарии.

**Варианты:** invokable-контроллер либо несколько связанных действий в одном контроллере. Длина метода — сигнал для чтения, не формальный критерий DDD. API Resource, transformer или простой явный mapper формируют ответ согласно контракту проекта.

**Проверка:** тело запроса не может подменить действующее лицо; правила модели работают при прямом вызове сценария.

## LAR-ERROR-01

Основание: [ARCH-FAIL-01](../core/boundaries.md#arch-fail-01).

**Решение профиля:** ожидаемые исходы переводятся в протокол на границе. Например, проект может выбрать 404 для отсутствия, 403 для запрета доступа и 409 для конфликта перехода или версии. Это решения API-контракта, а не требования DDD.

Контроллеру достаточно пути успешного выполнения, если общая обработка ошибок уже настроена. Локальный `try/catch` оправдан, когда сценарий представления умеет осмысленно восстановиться.

Внешнему потребителю выдаётся стабильный код и понятное сообщение. Техническая причина сохраняется для диагностики согласно правилам проекта. Сбой сети не преобразуется в «не найдено».

Метод HTTP и формат JSON выбираются по семантике API. Тело POST тоже может попасть в журналы: конфиденциальность зависит от настроек журналирования всей цепочки, а не только от размещения данных в теле.

**Проверка:** неизвестное исключение не маскируется ожидаемой бизнес-ошибкой; контракт ответа проверен функциональным тестом.

## LAR-QUEUE-01

Основания: [ARCH-USE-01](../core/application.md#arch-use-01), [ARCH-EFFECT-01](../core/application.md#arch-effect-01).

**Решение профиля:** входящий Job — адаптер сценария. Передавайте идентификаторы и необходимые данные сообщения; актуальную модель загружайте при исполнении.

Зафиксируйте, что означает повтор: переоценка текущего состояния, воспроизведение прежнего результата или отказ. Если важен момент исходного события, передавайте его отдельно от текущего времени обработки.

Интеграционные события, входные команды и внутренние задания могут иметь разные контракты. Не делайте Job корнем агрегата или единственным местом бизнес-правила.

**Проверка:** повтор задания не создаёт недопустимый второй эффект; долгоживущий worker не использует полномочия предыдущего задания. См. также [LAR-EFFECT-01](application.md#lar-effect-01).

## LAR-VALID-01

Основания: [ARCH-NORM-01](../core/boundaries.md#arch-norm-01), [TEST-CONTRACT-01](../core/testing.md#test-contract-01).

**Решение профиля:** FormRequest, VO и описание API проверяются на общей таблице примеров. Доменная проверка сохраняется для CLI, Job и прямого вызова сценария.

Правило `digits_between:10,12` допускает промежуточную длину. Для условия «10 или 12» используйте выражение или правило, точно передающее это множество. Значение со значимыми ведущими нулями сохраняйте строкой. См. [Validation](https://laravel.com/docs/13.x/validation#rule-digits-between).

Нормализацию выполняйте до построения ключа кэша и до обращения к репозиторию. Middleware HTTP может преобразовать вход, но прямой вызов сценария должен иметь согласованный контракт сам по себе.

**Проверка:** пробелы, пустое значение, промежуточная запрещённая длина, неверный тип и ведущие нули проходят через все применимые точки входа с ожидаемым результатом.

## LAR-PROTO-01

Основания: [ARCH-CONTRACT-01](../core/boundaries.md#arch-contract-01), [ARCH-FAIL-01](../core/boundaries.md#arch-fail-01), [TEST-CONTRACT-01](../core/testing.md#test-contract-01).

**Решение профиля:** форма JSON, HTTP-статус и заголовки проверяются отдельно. Для выбора JSON-рендеринга Laravel предоставляет `shouldRenderJsonWhen()`; механизм сам по себе не требует превращать все исключения в 500. См. [Error Handling](https://laravel.com/docs/13.x/errors#rendering-exceptions-as-json).

При собственном renderer сохраняйте смысл известных 401, 403, 404, 405 и 429 и необходимые заголовки, включая `Retry-After`, если он применим. Рассматривайте исключения маршрутизации и middleware вместе с ошибками модуля.

API может иметь несколько описанных форм ошибок. Заявлять единую оболочку следует, только если в неё действительно попадают все соответствующие ответы. Для списков проверяйте форму после сериализации: массив PHP с пропущенными числовыми ключами может превратиться в JSON-объект.

**Проверка:** сравните реальные ответы со схемой OpenAPI, включая неуспехи и запросы с различным `Accept`. Изменение одного translator не завершает изменение контракта, если прежние схемы и примеры остались.
