# Сценарии и сборка зависимостей

[Профиль](README.md).

## LAR-USE-01

Основания: [ARCH-USE-01](../core/application.md#arch-use-01), [ARCH-CONTRACT-01](../core/boundaries.md#arch-contract-01).

**Решение профиля:** прикладной сценарий — PHP-класс с явными зависимостями. Вход выражен простыми параметрами или DTO; результат — DTO, значение или документированный исход.

Действующее лицо приходит из доверенной точки входа, а не из произвольного поля запроса. Для фонового процесса определите собственные полномочия. Проверка доступа может быть простой проверкой в сценарии либо прикладным портом с адаптером к механизму авторизации проекта.

Допустим один обработчик на действие или сервис из нескольких связанных действий. Сценарий не получает HTTP Request, Eloquent Model или Query Builder.

**Проверка:** один и тот же сценарий вызывается из HTTP, CLI и задания без обхода правил доступа и модели.

## LAR-DI-01

Основание: [ARCH-COMPOSE-01](../core/boundaries.md#arch-compose-01).

**Решение профиля:** сервисные зависимости связываются в Service Provider. Контейнер разрешает интерфейсы согласно зарегистрированным реализациям. См. [Service Container](https://laravel.com/docs/13.x/container).

Параметры внешнего адаптера удобно передавать из провайдера. Доступ к конфигурации допустим и в инфраструктурном коде, если это явно выбранная зависимость. Для Domain и Application в данном профиле действует запрет на скрытые `config()`, `env()`, `app()` и `resolve()`.

Создание VO, DTO, сущностей и исключений через `new` допустимо в соответствующих компонентах. Контейнер не нужен для каждого объекта модели.

Выбирайте время жизни зависимостей осознанно: singleton не должен удерживать состояние запроса, пользователя или арендатора между заданиями и запросами долгоживущего процесса. Laravel поддерживает в том числе scoped-привязки. См. [Container: Binding Scoped Singletons](https://laravel.com/docs/13.x/container#binding-scoped).

**Проверка:** binding ведёт к нужной реализации, а тест сценария может передать зависимость напрямую.

## LAR-TX-01

Основания: [ARCH-CONS-01](../core/application.md#arch-cons-01), [ARCH-PORT-01](../core/boundaries.md#arch-port-01).

**Решение профиля:** сценарий задаёт границу транзакции через прикладной порт, реализация которого использует соединение Laravel. Этот порт нужен сценариям с транзакционной работой.

```php
<?php

declare(strict_types=1);

namespace DddGuide\Booking\Infrastructure;

use Closure;
use DddGuide\Booking\Application\Transaction;
use Illuminate\Database\Connection;

final readonly class LaravelTransaction implements Transaction
{
    public function __construct(private Connection $connection) {}

    public function run(Closure $operation): mixed
    {
        return $this->connection->transaction($operation);
    }
}
```

Интерфейс `Transaction` определён в [примере](example.md#сценарий). Repository и Transaction должны использовать одно соединение. Если репозиторий сохраняет несколько записей, вся операция входит в ту же транзакцию.

Laravel откатывает транзакцию при исключении; механизм также поддерживает повтор при deadlock. При включении повторов тело операции должно заново загружать модель и безопасно повторяться. См. [Database Transactions](https://laravel.com/docs/13.x/database#database-transactions).

Если адаптер заранее оборачивает SQL-ошибку в собственное исключение, проверьте, сможет ли механизм транзакции распознать причину для повтора. При необходимости переводите ошибку за внешней границей транзакции. В сквозном примере автоматические повторы не включены.

**Вариант:** прямой `DB::transaction()` в прикладном коде возможен в упрощённом профиле, зафиксированном ADR. Он не соответствует базовому выбору изоляции Application в этом руководстве.

**Проверка:** исключение не оставляет частично сохранённое состояние. Отдельно проверяется конкуренция по [LAR-LOCK-01](persistence.md#lar-lock-01).

## LAR-EFFECT-01

Основания: [DDD-EVENT-01](../core/domain-model.md#ddd-event-01), [ARCH-EFFECT-01](../core/application.md#arch-effect-01).

**Решение профиля:** доменная модель не отправляет задания и уведомления самостоятельно. Сценарий или его инфраструктурное окружение связывает факт с последующими действиями.

Laravel позволяет отложить отправку задания до commit через `afterCommit()` или настройку `after_commit`; при rollback такие отложенные задания отбрасываются. См. [Jobs and Database Transactions](https://laravel.com/docs/13.x/queues#jobs-and-database-transactions).

Это механизм порядка выполнения. Для обязательной доставки проект дополнительно решает разрыв между commit и передачей задания: например, сохраняет outbox-запись вместе с агрегатом, а отдельный процесс отправляет её с повторами. Получатель распознаёт дубликаты, если повтор эффекта недопустим.

**Проверка:** отдельно моделируются rollback, сбой отправки после commit и повторная доставка. Доменное событие не обязано совпадать по форме с внешним сообщением.
