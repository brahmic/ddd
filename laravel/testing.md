# Проверки реализации

[Профиль](README.md).

## LAR-TEST-01

Основания: [TEST-BEH-01](../core/testing.md#test-beh-01), [TEST-USE-01](../core/testing.md#test-use-01).

**Решение профиля:** Domain и изолированные сценарии проверяются обычными тестами PHP без загрузки приложения. PHPUnit или Pest выбираются по стандарту проекта.

Для доменной модели проверяйте таблицу переходов, равенство значений и восстановление. Для сценария — результат, доступ, сохранение и обработку ошибок портов. Передавайте фиксированные часы и подходящие реализации в памяти.

Тесты, использующие контейнер, фасады или БД Laravel, относятся к проверкам с загрузкой приложения. Различие unit- и feature-наборов описано в [Testing](https://laravel.com/docs/13.x/testing).

**Проверка:** доменные тесты запускаются без сетевых вызовов, БД и глобального времени. Несущественный внутренний рефакторинг не ломает их.

Каталог `Unit` сам по себе не гарантирует изоляцию. Если класс теста наследует Laravel TestCase, приложение загружается. Выбирайте базовый класс по реальным зависимостям проверяемого поведения.

## LAR-TEST-02

Основание: [TEST-ADAPTER-01](../core/testing.md#test-adapter-01).

**Решение профиля:** инфраструктурные гарантии подтверждаются отдельными интеграционными проверками.

| Адаптер | Существенные проверки |
| --- | --- |
| Репозиторий | Сохранение и восстановление, отсутствие, неизвестные значения |
| Транзакция | Rollback, использование того же соединения, атомарность нескольких записей |
| Конкуренция | Устаревшая версия, условное обновление или блокировка на целевой СУБД |
| HTTP-клиент | Успех, отсутствие, повреждённый ответ, ошибка и допустимый повтор |
| Кэш | Область ключа, TTL, обновление после записи |
| Доставка | Rollback, момент отправки, восстановление после сбоя и повтор |

Для Laravel HTTP-клиента используйте `Http::fake()` и `Http::preventStrayRequests()`, чтобы незамоканный запрос не ушёл в сеть. Это ограничение относится к этому клиенту, а не автоматически ко всем сетевым библиотекам процесса. См. [HTTP Client: Testing](https://laravel.com/docs/13.x/http-client#testing).

Средства подготовки БД, включая `RefreshDatabase`, описаны в [Database Testing](https://laravel.com/docs/13.x/database-testing). При проверке реального commit и after-commit поведения учитывайте внешнюю транзакцию тестового окружения: тест должен действительно завершить нужную транзакцию.

`Event::fake()` и `Queue::fake()` полезны для проверки отправки. Для проверки логики обработчика вызывайте его отдельно; fake не доказывает выполнение бизнес-эффекта. См. [Mocking](https://laravel.com/docs/13.x/mocking).

**Проверка:** in-memory repository и SQLite не объявляются доказательством семантики другой СУБД. Конкурентные случаи используют независимые соединения и контролируемое пересечение операций.

Для повторов HTTP-запроса полезна матрица: временный сбой → успех; отказ без повтора; исчерпание попыток; ошибка соединения → успех или окончательный сбой. Проверяйте число фактических отправок и существенные поля исходящего запроса. Это дополнение к проверке последнего результата.

## LAR-TEST-03

Основание: [TEST-ARCH-01](../core/testing.md#test-arch-01).

**Решение профиля:** автоматизируйте проверяемые соглашения из [таблицы зависимостей](structure.md#направления-зависимостей).

Для Domain и Application контролируйте импорты `Illuminate`, обращения к фасадам и глобальные helpers. Для модулей — доступ к внутренностям соседнего контекста. Учитывайте исключения, принятые в ADR, чтобы правило проверяло реальный профиль.

HTTP-тест проверяет форму входа, аутентификацию, перевод исходов и схему ответа. CLI- и Job-тесты добавляются для значимого собственного поведения этих адаптеров.

Используйте существующие команды проекта для тестов, форматирования и статического анализа. Процент покрытия и атрибут конкретного раннера не являются критериями DDD.

**Проверка:** результат содержит сведения о проверенных сценариях и ограничениях. Не выдавайте синтаксическую проверку примера за успешную интеграцию с БД.

Добавьте необходимые проверки [API-контракта](presentation.md#lar-proto-01), [сборки настроек](operations.md#lar-config-01) и [диагностики](operations.md#lar-obs-01). Подмена зависимости полезнее полного отключения проверяемой ветви по признаку окружения.
